# 路由与上下文交接

[English](workflow.md) · [简体中文](workflow.zh-CN.md)

本说明配合桌面版配置使用。安装后的 AGENTS 文件保存简明规则，角色 TOML 定义模型与职责，本文记录任务矩阵和交接格式。不需要 Codex CLI。

## 主智能体与子智能体的边界

主智能体维护用户目标，管理路由、上下文、依赖、冲突、向用户澄清和最终汇总。核心技术工作按有边界的交付物委派。子智能体可以在任务内自主调查、选择工具、作局部决定；范围变化、需求冲突和新授权需求交回主智能体协调。

sol_worker 可以从目标开始，细化需求、业务规则、验收标准、常规技术方案、依赖拆分、交互/视觉方向、适用技能下的设计产物、测试策略和实施诊断。需要向用户澄清的问题由主智能体统一处理。Astra 为重大架构、公共接口、数据模型和取舍以及困难根因提供建议，并保持只读。主智能体检查建议是否适用并协调后续影响，无需重新完成同等分析。专业验证可以委派给审查者；主智能体确认验证证据覆盖目标且对应实际产物。

上下文已经完整的短任务可由主智能体直接完成。该例外不能绕过实时浏览器和桌面工作固定 Luna 的规则。不应为每条命令创建代理，也不要求每项任务都经过所有角色。

## 任务矩阵

这些默认分工表达职责，不代表已实测的质量或费用排名。

| 情境 | 负责人 | 边界或升级 |
| --- | --- | --- |
| 负责目标、向用户提问澄清、排优先级、路由和调度依赖 | 主智能体 | 在交接中持续同步决定和上下文 |
| 将目标细化为需求、业务规则、验收标准、常规技术方案、依赖拆分或测试策略 | sol_worker | 需向用户确认的问题交主智能体；重大架构/协议/数据模型/取舍交 Astra |
| 提出交互与视觉方向或产出设计材料 | sol_worker | 有适用设计技能时使用，并明确范围与验收条件 |
| 查代码、文档、调用方或事实 | luna_reader | 返回证据与搜索范围，避免重复已有搜索 |
| 实现清楚且有边界的修改或已知批量更新 | luna_worker | 在约定范围内决定实现细节 |
| 实现复杂功能或作较深入的实施判断 | sol_worker | 重大架构或接口决定交 Astra 建议 |
| 决定重大架构、公共接口、协议、数据模型或取舍 | astra_advisor | 只读；给出具体决定、理由、影响范围、关键不变量和验证标准 |
| 实施已选定的交互或视觉设计 | luna_worker / sol_worker | 主智能体按复杂度路由，并提供设计材料和验收条件 |
| 操作实时浏览器或桌面、采集实时 UI 证据、运行浏览器/桌面 UI E2E | luna_browser | 固定 GPT-6 Luna High；不操作浏览器或桌面的服务端 E2E 按普通测试路由 |
| 审查实时 UI 报告或已保存的截图、DOM、日志、记录 | sol_reviewer / sol_worker | 分析提供的证据，不接管实时操作 |
| 制定测试策略 | sol_worker | 明确覆盖范围、有意义的用例以及是否涉及浏览器操作 |
| 编写测试代码 | 实施者，按任务范围选择 Sol 或 Luna | 浏览器/桌面自动化及相应 UI E2E 由 luna_browser 执行；普通服务端 E2E 按普通测试路由 |
| 运行普通非浏览器检查 | 实施者或 sol_reviewer | 报告实际命令和结果；仅因必要关卡或具体风险扩大检查 |
| 调查性能、安全或并发问题 | sol_worker / sol_reviewer | 重大或未解决的根因决策交 Astra；实时 UI 测量仍由 Luna 操作 |
| 执行迁移、依赖升级、构建或 CI/CD 修改 | luna_worker / sol_worker | 按复杂度路由；适用时附实施验证和恢复或交接说明 |
| 解决 Git 冲突、准备 PR 修改或协调跨仓库工作 | 主智能体协调；worker 执行；reviewer 验收 | 主智能体决定仓库归属与依赖；不假设工具权限或隔离；外部发布须符合用户授权 |
| 更新文档、脚本、技能、MCP 或插件集成 | luna_worker / sol_worker | 按范围和实施判断路由；权限或外部操作需求交主智能体 |
| 重要补丁审查、集成验证 | sol_reviewer | 独立审查应使用与实施者不同的代理 |
| 向用户汇总结果与未解决问题 | 主智能体 | 核对产物与验证证据 |

外部操作仍应在用户授权范围内。委派不会增加权限。

## Astra 建议后的修复闭环

Astra 诊断困难根因时，应给出具体诊断、有边界的执行步骤、关键不变量和验证标准。主智能体将证据与约束一并交给 sol_worker 执行。如果修复仍失败，主智能体先根据新证据判断属于方案缺口、执行错误还是环境/工具限制。方案可能不足或新证据可能改变原决定时，再咨询 Astra；执行错误和环境/工具阻塞先交给适合的 worker 处理。没有新证据时不要原样重复同一建议。该闭环不改变 Astra 的只读职责，也不会把实时浏览器/桌面操作权从 luna_browser 转走。

## 浏览器与桌面所有权

所有实际 computer-use、CDP 查询、浏览器自动化和实时 UI 证据采集，均由 luna_browser 使用 GPT-6 Luna High 完成。通过 shell 脚本或其他包装执行浏览器操作同样适用。更强模型可以分析保存的证据、提出后续调查建议，实际操作仍交给 Luna。

普通非浏览器测试可以由执行者或审查者完成。测试若主动驱动浏览器，由 Luna 运行并把报告交给审查者。

会相互影响的浏览器、桌面或远端业务状态，同一时间指定一名操作者。不同标签页不一定隔离登录或后台记录。其他代理使用保存的证据，或使用已经确认不会互相干扰的独立环境。操作报错时，Luna 先观察是否已经生效，再决定是否重复提交。

代理上下文不等于共享 REPL。交接时提供 URL 或会话标识，但接手者应重新获取目标与当前状态，不能依赖其他代理的内存变量或已过时的元素句柄。

## 委派约定

使用简短结构化消息，避免默认转发完整对话：

~~~text
目标与验收条件：
相关背景和已确认决定：
负责的文件或资源：
范围内允许自主决定的事项：
证据与原始资料位置：
依赖，以及需要返回协调的情况：
~~~

能在委派说明中提供充分信息时，优先独立上下文。相关后续工作在上下文、模型和职责仍适用时复用已有代理。用户补充的新约束应传给受影响的代理；早先传出的上下文副本不会自动保持最新。

每次委派负责完整结果。避免查阅者和执行者分别重做同一调查。保留其他协作者的修改，同一可写文件避免同时分给多个负责人。

## 结果约定

~~~text
状态：完成 / 部分完成 / 阻塞
产物或当前现场：
实际验证及证据：
未确认的操作：none / 具体操作及已观察状态
失败假设、对应改动和验证结果：
下一项未决事项或依赖：
~~~

阻塞报告应让接手者继续工作，而不必重复已失败的尝试。证据摘要中不包含凭据。

审查者可以生成必要测试缓存和报告，但不得为让检查通过而修改应用代码、断言、配置或依赖。发现失败后返回证据，由主智能体交给执行者修复。

## 升级与完成

重大架构、接口或数据模型决策、重要取舍、明确要求的深度评审，或两轮有证据修复后仍未解决的根因交给 Astra。每轮包含假设、对应改动以及针对失败现象的验证。轮次跨代理累计；工具故障或权限不足属于能力问题，不自动算推理失败。

复用适用的决定。分析升级不改变 Luna 的浏览器操作权。角色尚未加载但支持显式模型选择时，使用准确模型与完整角色指令；否则报告能力缺口，不静默替换模型。

所需产物和检查证据覆盖用户目标后，主智能体组织交付。无需重复专家验证，但必须解决缺失或矛盾的证据。较大变更或重要风险需要独立审查，小改动默认无需单独安排审查者。

## 评估记录

~~~text
任务和验收条件：
角色/模型分配及原因：
交接次数和重复工作：
实际模型用量或费用（可获得时）：
验收结果、失败和返工：
总耗时，包括等待：
保留分配 / 调整 / 证据不足：
~~~

配置有效、角色被发现、工具可见和任务成功执行是不同的检查。尤其是，看见 computer-use 工具不等于已经能操作目标应用。现有桌面任务可能保留旧角色定义，应在新的桌面任务中验证更新。
